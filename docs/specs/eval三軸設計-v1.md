#### 軸三的出題與「保證未見」機制

**兩級題目（定案（執行端）——級別與題數維持草稿設計，依據見 §三.2 的 n 地板）：**
- **近未見**（6 題）：清單既有類別、全新題材與名詞。測「學到的是揮棒方式還是那句台詞」。補丁修訂二已警告：「測試題跟範例太像，測到的是她會不會背」。
- **遠未見**（6 題）：**類別本身**不在清單、不在任何語料裡的情境（例：被誇獎、兩人同時下矛盾指令、對方突然講超正式的話、被請求幫忙保密她自己講過的話……以上僅示例，正式題不得寫進本文件——寫進來就進了 repo，將來可能被讀進 context）。測硬套。

**「未見」要防的洩漏通道（逐一列舉）：**

| # | 通道 | 位置 |
|---|---|---|
| 1 | 角色卡內文（703 token）與其中範例 | 生產 payload |
| 2 | 轉接層 few-shot（16 則，`messages+boundary`） | `llm-proxy` |
| 3 | 👍 標記庫（會變成 few-shot 與微調語料） | `llm-proxy\marker-memory.jsonl` |
| 4 | 未來種子對話 10–20 組與幾百筆微調語料 | 未產生 |
| 5 | 歷史測試協議（四題、二十輪劇本）與 v28 的 216 筆等結果 | `card-experiments-v2x\` |
| 6 | 情境測試清單本身——若有人拿清單題寫種子對話，清單就從尺變成教材 | `docs\character\` |

**保證機制：**
1. **封存題庫**：未見題庫獨立成檔，記 hash；題目**不出現在任何會被角色讀到或被語料作者當參考的文件裡**。存放位置已定案，見 §六.2。
2. **機器查重是最後一關**：每次「凍結訓練語料」與「跑 eval」之前，用骨架比對（`card-experiments-v29\formula_v29.mjs` 的功能詞骨架＋LCS 邏輯，需寫一個離線 adapter 讓它比「題目 vs 語料」而不是「回覆 vs 回覆」）掃題庫對通道 1–5 的全部文本。**字面 n-gram 查重不夠**——本專案的教訓就是字面比對抓不到「句型相同、名詞不同」（00 原則五）。
3. **撞到就換題**：訓練語料來自真實對話，優先權在語料；被撞到的 eval 題**作廢換新**，作廢紀錄保留（不然「換過題」這件事會沈默地消失，違反原則十）。
4. **eval 對話不得回收**：eval 跑出來的 session 一律標記，**永不**進 👍 匯出、few-shot、訓練語料。不標記的話，跑一次 eval 就污染一次題庫。
5. **人腦洩漏**：`01-專案定位與需求規格-v2.1.md` §八承認「我會不自覺地配合她」。寫語料的人（客戶＋規劃端）看過 eval 題之後，寫語料會無意識靠近。緩解：遠未見題可用 `01` §八順位 4 的路線產生（強模型合成對抗輸入、人工篩），並**每個訓練週期輪換一部分遠未見題**；順位 3 的紅隊 session（朋友想辦法讓她崩）天然就是遠未見題的來源。出題分工已初步定案，見 §六.4。
6. **跨 session 記憶目前結構性為零**（補丁修訂二：「新對話零帶入」），所以「她這一版看過這題」不構成洩漏；洩漏唯一的路是**進了語料或 prompt**。Phase 4 記憶層上線後這一段要重寫（原則九）。

客戶時間是稀缺資源（高中生）：每個 eval 週期客戶要看的東西控制在**一份盲測表（10–14 組）＋爭議題**，約 20–30 分鐘。其餘放在 review 資料夾後段（紀律第 5 條：`讀我.txt`，不讓客戶翻原始資料夾）。

### 2.3 盲測協定（沿用 v29 先例）

先例：`card-experiments-v29\build_blind_v29.mjs` ＋ `ENVIRONMENT.md`：「盲測表（10 組、模型名隱藏、**固定種子洗牌**）…對照表在 `blind-key-DO-NOT-OPEN.json`。客戶判完才看。」

沿用五條規則（v29 §五）＋ before/after 適配：
1. 條件名（base / ft-vN）隱藏，標甲／乙；**每組內位置用固定種子洗牌**（種子記錄在案，v29 用 mulberry32 seed 2029 的形狀）。
2. 對照表另存一檔，**不放進 review 資料夾**，客戶判完才開。
3. 盲測表內**不放任何客觀指標**（字數、公式率都會洩漏身分）。
4. 回應剝除 ACT marker 後呈現。
5. 挑組規則要寫出來，且不准挑對某一方有利的題。
6. **已知限度（推測，不可修復）**：微調後的文風本身可能自帶指紋，盲不完全；照樣盲，並記錄客戶是否「猜得出哪邊是哪邊」。

## 三、跑法設計（本輪不跑）

### 3.1 兩段分離：批次生成（GPU）／離線判讀（無 GPU）

- **生成段**：獨佔 GPU 那條 lane，序列執行，不與其他 GPU 線撞（v31 §四：「平行的單位不是 session，是那張卡」；v32 §四同）。生成中**不開任何 subagent**（v29 事故：4 筆首字是在 subagent 跑檔案運算時量的）。工具基礎可沿用 `card-experiments-v29\replay_m3_v29.mjs` 形（不經桌面版、批次友善）＋ `card-experiments-v30\run_matrix_v30.mjs` 形（經桌面版）。輸出沿用既有 `results-*.json` 格式，讓現成偵測器直接吃。
- **判讀段**：純檔案運算，可開 subagent——偵測器、查重、盲測表、review 資料夾（v31 §四明列 eval 相關離線工作為可平行項）。
- **原則四的張力要交代**：replay 不是「系統實際走的那條路」。緩解：每個 eval 週期抽題走真實桌面版路徑對照 replay 輸出，確認前綴一致（capture 比對即可，不必比內容逐字）。頻率已定案，見 §六.5。
- eval 輪**不量延遲**——快是另一個任務，混在一起兩邊都量壞（scope 紀律）。

### 3.2 n 要多少（定案（執行端））

00 §五的原話是量延遲的教訓：「報分布，不要只報中位數——這台機器的延遲是雙峰的，**n=5 分不開，要 ≥12**」。本設計把「≥12 才准比」升格為**所有 pass/fail 比率的通用地板**。理由：這是本專案唯一一條有實測依據的樣本量規則；在文本 pass/fail 上沒有更好的本地證據之前，取同一地板是保守選擇（原則十一：不在沒數字的地方發明一個更寬的數字）。

| 單位 | 定案值 | 依據 |
|---|---|---|
| 每題重複 | **3 次，全新 session，不重生成** | v24 協議先例（每步 4 題 × 3 次） |
| 每個會拿來停損的比率，每條件題數 | **≥12 題** | 00 §五地板 |
| 軸二題量 | 清單 ✅ 12 條 × 3 | — |
| 軸三題量 | 近 6 ＋ 遠 6 × 3 | — |
| 軸一 | 複用上述回應 ＋ 二十輪劇本 × ≥2 場 | — |
| 估算 | 每條件約 (12＋12)×3＋2×20 ≈ **112 次生成**（估算值，非實測） | — |

- **報分布不報中位數**；每題三次的逐次結果都留。
- 延遲的 ABAB 交錯搬到文本生成上會逼迫每題換載模型（成本高）。**推測**：文本內容與機器忙閒無耦合（雙峰是延遲現象），故 before/after 可各自整批跑，但必須同一個 Ollama 版本、同環境快照、淨機；此推測要標記在結果裡，若客戶盲判出現無法解釋的批次效應，回頭改成交錯。
- 🔴 **Ollama 會自我升版且動過數字**（MEMORY／v31 §八）：before 與 after 之間版本若漂移，依原則三 baseline 作廢重跑。每次生成段開頭記版本、殺系統匣 `ollama app.exe`。

### 3.3 環境快照（每筆都記，沿用清單附錄格式）

模型 tag、角色卡版本、few-shot 模式與筆數、取樣參數、Ollama 版本、新開 session、機器負載、**訓練版本與語料 hash**（`num_step` 無關——本 eval 不含 TTS）。環境不同就不比，或標「無可比基準」（原則三）。

## 四、與訓練的接口（before/after 協定）

### 4.1 流程

1. **凍結**：evalset 版本＋hash、判準版本（人格判準 v1.0＋清單 v1.1 套用補丁後）、查重通過證明（題庫 vs 訓練語料）。
2. **訓前 baseline**：完整三軸跑一次、存原始 transcript。「symptom 跟原本一模一樣」意味著比較對象必須是**存檔資料，不是記憶**。
3. 訓練（夜間切片；每版存檔可回滾——v29 附錄一路線：「QLoRA 小步實驗、每版存檔、A/B、可回滾」）。
4. **訓後**：同一套 evalset、同環境，跑一次。
5. 離線判讀＋before/after 盲測表。
6. 對照停損表。**通過**：該版成為新 baseline。**未過**：回滾、記錄該版與症狀（原則七：缺口要被看見）。

### 4.2 停損表（v1 定案：以「相對訓前 baseline 的方向」為正式停損，理由見 §六.1）

| 軸 | 指標 | 停損條件（相對訓前 baseline） |
|---|---|---|
| 自然度 | 客戶盲判「不通順」數 | 上升即不部署（單題抖動的覆核規則見 §六.1） |
| 自然度 | 語意公式率 | 🔴 新 base 的基線是 **0**（v30 §實測：三個換掉的模型公式率全部歸零）——**任何 >0 都是警報**，人工確認後即停 |
| 自然度 | 簡體字、`史`/幻史命中 | 從 0 變有即停查 |
| 人格 | 失敗清單 #1/#2/#3（助理自稱/道歉/給建議） | 出現次數上升即不部署 |
| 人格 | 失敗清單 #4 沒揮棒 | 上升＝往「安全的無聊」漂，警報 |
| 泛化 | 遠未見題硬套 | **≥1 題人工確認硬套即停整條訓練線**（這就是「權重裡的範本庫」現形） |
| 泛化 | 見過 vs 未見分數差 | 見過題進步、未見題持平或退步 → 背誦特徵，停查資料 |
| 錨點 | 動態錨點排行 | 出現**新**錨點（不限舊詞表）即警報（v30 附錄二） |

原則八：停損觸發不是降標準的理由，是回滾＋查資料的理由。

### 4.3 已知的接口外債（記錄，不在本設計內解）

微調資料怎麼從 10–20 組長到幾百筆「中間那段沒有解法」、災難性遺忘無公開解（皆 v30 附錄三）；語音接上後整套題庫是打字版、要重跑且不可與打字版直接比（補丁修訂四、原則三）——此項與 §七 的銜接點一相關。

## 五、評分表格式（要能被引用成判準級文件）

`人格判準.md` 的效力來自「每一條都來自具體情境的實際判斷」。評分表的設計目標：**讓每一格判定將來都能被一句話引用**，供規劃端蒸餾出判準級文件。

**引用鍵格式（定案（執行端））**：`{軸}-{未見級}-{題號}-r{重複次}@evalset-v{N}`，例 `泛-遠-07-r2@evalset-v1`。

### 每筆（per-item）欄位

| 欄 | 內容 |
|---|---|
| 引用鍵 | 如上，全域唯一 |
| 軸／情境類別／來源 | 自然度・人格・泛化／清單條號（含清單版本）或新造批次 ID 或劇本輪次 |
| 未見等級＋查重證明 | 見過/近未見/遠未見；骨架查重比對過哪些語料（各附 hash）、結果 |
| 輸入全文 | 含時間戳前綴原樣 |
| 回應全文 | marker 原樣一份＋剝除後一份 |
| 自動篩逐項 | 公式（命中/最大群/主骨架）、史、簡體、字數、錨點、硬套候選、照抄 |
| 人工判定 | 通順（✅/❌、判者、盲或非盲）；人格（✅/⚠️/❌＋**引用的通則/失敗清單條號**）；泛化（硬套 有/無/存疑＋一句話依據） |
| 盲測欄 | 盲標籤、所在盲組、種子、key 檔路徑 |
| 環境快照 | §3.3 全項 |
| 訓練版本 | base / ft-vN＋語料 hash |
| 備註 | 清單紀律①：判準沒寫但很好的回應記在這，標 👍 候選——**但 eval session 的回應不得真的進 👍 庫**（§一.4），只作為判準修訂素材 |

### 每次（per-run）彙總欄位

每軸每條件：分布（逐題逐次，不只中位數）、失敗清單命中直方（按條號）、公式率、見過/未見兩欄並排、⏳ 條目現況（永遠列出，當進度基準）、「沒跑」與「通過」分開寫、本次作廢/換掉的題目清單。

## 六、六個待決點的處理（草稿 §六逐一結案）

### 6.1 停損門檻的絕對值 → **定案（執行端）：v1 不設絕對值，以相對方向為正式停損**

理由：訓前 baseline 一次都還沒跑，此刻寫任何絕對值都是在沒有數字的地方下推論（原則十一），而且偏向「讓表看起來完整」這個我們想要的答案。§4.2 的表其實只有兩格天然是絕對值，且各有實測或邏輯依據：公式率 >0（依 v30 實測基線 0）、遠未見硬套 ≥1（一題就證明範本庫存在，沒有「可容忍的一點點範本庫」）。其餘維持方向性條件。
補充定案（抖動處理）：凡「上升即不部署」的指標，若上升量僅 1 筆，**該題原環境重跑一輪覆核**（3 次重複已內建，覆核是第 4–6 次），覆核仍在才算數——這是防止單次抽樣抖動誤觸停損，不是容忍量。
【待規劃端】baseline 跑完後，若要在方向條件之上加絕對門檻（例如「不通順數絕對值 ≤N 才准部署」），由規劃端依 baseline 實測值修訂，並升版 evalset。

### 6.2 未見題庫的存放位置與讀取權限 → **定案（執行端）**

- 位置：`eval-vault\`（新資料夾，純英文路徑——執行端紀律 10）。**不在 `docs\` 之下**——`docs\` 是常駐文件區，會被規劃端與執行端視窗例行讀入 context。
- 命名沿 v29 的隔離先例（`blind-key-DO-NOT-OPEN.json`）：題庫檔命名 `questions-DO-NOT-OPEN-evalset-vN.json`，資料夾放一份 `README-DO-NOT-OPEN.txt` 寫明：只有「跑 eval 生成段的執行端 session」可讀；**寫語料、寫角色卡、寫 few-shot 的任何 session（人或 agent）不得開啟**；違反即題庫視同污染，被看過的題作廢換新（§一.3 的作廢紀錄機制照用）。
- 進 git：**要**。理由：作廢紀錄與換題歷史必須可追（原則十——「換過題」不能沈默消失），且 hash 要能對到某個 commit。隔離靠的是「不放 docs\、檔名明示、規範明文」三層，加上機器查重當最後一關兜底（§一.2）——就算哪天被讀進某個 context 而人腦洩漏進語料，骨架查重仍會在凍結時撞出來。
- 常駐文件（specs、交接書、ENVIRONMENT.md）永遠只准引用**題目的引用鍵與 hash**，不准引用題文。

### 6.3 選配 LLM 輔助篩 → **定案（執行端）：v1 預設關**

理由：§2.1 已列的繞過風險（通用裁判偏好禮貌完整＝我們的失敗形狀；會錯殺「揮了沒中」）在沒有實測校準前無法排除，而 v1 的量（每條件約 112 筆）人工加篩子還吃得下，開它的收益不明、風險已知。
若未來量長大要開：**開啟權【待客戶】**（它動的是「客戶要看什麼」這件事）；開啟後的硬限制照 §2.1——只准標「疑似語意不通」候選、永不碰人格分、永不出最終判定；所用模型與版本記入環境快照。

### 6.4 遠未見題由誰出 → **定案（執行端，初版做法）＋【待規劃端】長期配比**

evalset-v1 的遠未見 6 題：由**規劃端在一個不載入訓練語料、不載入 few-shot、不載入角色卡內文的獨立視窗**出題（規劃端是唯一同時懂判準又不直接寫語料正文的角色；獨立視窗是對 §一.5 人腦洩漏的最低成本緩解），出完直接進 `eval-vault\`，不經任何常駐文件。
輪換規則：每個訓練週期輪換 **≥2 題（1/3）**；被查重撞掉的另計。
補充來源（可得時優先於規劃端出題）：紅隊 session 素材（`01` §八順位 3）、強模型合成對抗＋人工篩（順位 4）。
【待規劃端】三種來源的長期配比、以及紅隊素材開始產出後是否全面接手遠未見題。

### 6.5 replay 與真實路徑的抽查頻率 → **定案（執行端）：每 eval 週期 3 題**

取草稿區間（2–3）的上緣，理由：抽查只比 capture 前綴、不比內容逐字，成本是分鐘級，而它守的是原則四（本專案在「等價路徑」上翻過車：`think:false` 在 `/api/chat` 有效、在 `/v1/chat/completions` 被丟棄）。規則：3 題中**任何一題**前綴不一致 → 該週期全部 replay 結果標「無可比基準」，查因修復後整段重跑，並回報主 agent（原則三、十）。

### 6.6 前置作業排程 → **定案（執行端）：固定為訓練線開工的門檻序列（gate）**

順序不可調換：
1. **套用清單修訂補丁 v1.1**（純文件編輯，無 GPU）：改 `情境測試清單.md` 為 v1.1、舊版另存 `情境測試清單-v1.0.md`、`人格判準.md` 補「她叫什麼」一節（補丁「套用之後」三點全做）。
2. **出題與封存**：近未見＋遠未見題進 `eval-vault\`，記 hash（§6.2、§6.4）。
3. **查重**：題庫 vs 洩漏通道 1–5 全文本，骨架層（§一.2 的離線 adapter 要先寫好——這是唯一要新建的工具）。
4. **凍結 evalset-v1**：版本＋hash＋判準版本＋查重證明，四樣齊才算凍結（§4.1 第 1 步）。

時點：v32 收尾後的第一個文件工單；1–4 全程無 GPU，可與其他線平行（v32 §四），但**任何微調訓練不得在第 4 步完成前開跑**——沒有凍結的 evalset 就沒有 baseline，沒有 baseline 的訓練就是盲修（v30 附錄一）。

## 七、v32 之後的聲音維度：「說書人味／像不像唸稿」要不要進 eval 軸

### 背景

v32 的驗收結果：13 個候選（OmniVoice 克隆型／Kokoro、艾粒固定說話人）客戶盲聽**全部不合格，症狀一致**——「說書人味／配音員腔」，成因在引擎上游（`docs\specs\v32-spec.md` §〇）。v32 §六已把「**像不像在唸稿**」加進本輪試聽包評分表。問題：這個維度要不要進本文件的 eval 軸體系。

### 利（進軸的理由）

1. 它是目前**最大的一個驗收失敗來源**，且會隨引擎、參考音、開關的每次改動反覆發生——「沒有 eval 就分不出是誰造成的」這句話對它同樣成立。
2. 協定雛形已存在且與三軸同構：v31 補丁 A／v32 的試聽包規則（中性代號、對照表另存、固定句組、至少一半取自 Kamie 實際講過的話）就是 §2.3 盲測協定的聲音版，複用成本低。
3. 不進任何 eval 體系的話，聲音判定會退回「憑感覺變好了」——正是清單存在要防的事（`01`：唯一能分辨「變好了」和「感覺變好了」的工具）。

### 弊（不併入三軸的理由）

1. **量的不是同一件事（原則三）**。三軸吃 LLM 文本輸出，變因是模型／角色卡／few-shot／語料 hash；聲音維度吃 TTS 音訊，變因是引擎／參考音／`t2s_input`／`normalize_loudness`／合併開關。綁進同一套 evalset，換一次 TTS 引擎就得作廢文本 baseline（或反過來），而 v32 正處於引擎大概率要換的階段——本專案被「兩個數字量的不是同一件事」騙過至少 18 次，不要主動再造一個。
2. **自動篩子近乎為零**。「說書人味」目前查不到任何本地可跑的客觀 proxy（v32 §一⑤：連處理過這個問題的前輩都沒有；原則六：查不到就寫查不到），整條維度 100% 靠客戶耳朵——而 §2.2 已把每週期客戶預算壓在 20–30 分鐘，再塞盲聽會把預算撐爆或稀釋文本判定。
3. **觸發時機不同**。文本三軸的觸發是「每次微調前後」；聲音維度的觸發是「每次 TTS 側改動」。綁死會逼迫不必要的整套重跑，違反 scope 紀律（v32 §〇界線：純 TTS 那輪不碰 LLM，反之亦然）。
4. 現在就定聲音判準的細則，是在 v32 線 1／線 2 實測出來之前下推論（原則十一）——連「唸稿感在參考音還是在權重」都還沒有答案。

### 建議【建議，待規劃端】

1. **不併入三軸，也不設為第四軸。** 另立「**聲音 eval**」為獨立軸組（暫名：唸稿感／穩定／音色——即 v32 評分表欄位的常設化），**獨立文件、獨立 baseline、獨立停損**，等 v32 線 1／線 2 結果出來後再定稿細則。
2. 兩邊**共用紀律、不共用數字**：共用 §2.3 盲測協定與 §五記錄格式（引用鍵加 `聲-` 前綴；環境快照加 TTS 欄——引擎與版本、參考音 hash、`t2s_input`、`normalize_loudness`、合併開關、`num_step`）；兩邊結果**永不互比、不算差值**（原則三）。
3. 銜接點一：語音鏈路接上後，整套情境題庫要語音重跑且不可與打字版直接比（補丁修訂四）——**屆時**「端到端 eval」自然成題，是否升格為正式第四軸，等那時依實測再決定（原則九、十一）。
