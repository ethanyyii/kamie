## 一、角色分工

🔴 **規劃端與執行端是兩個獨立審查者，互相抓漏洞、互相質疑方向——不是指揮與執行。**

客戶原話（v59，完整未節錄）：

> 「你跟 claude code 就是兩個個體,你們可以互相討論互相抓漏洞跟方向,
> 而不只是一味地叫 claude code 去做你認為對的事,你讀不到碼,claude code 讀的到,
> 而你知道我要甚麼,而 claude code 比較不清楚,你有技術背景知識,
> 所以你知道 claude code 哪些決策有風險或要取捨,你不擋認為高價值就交到我面前」

| 角色 | 是誰 | 手上有的 | 負責 | 🔴 不該做 |
|---|---|---|---|---|
| **客戶** | 使用者 | **知道成品要長怎樣** | 決定成品的取捨、**最終驗收** | 不需要懂技術、不需要讀報告 |
| **規劃端** | Claude 對話視窗 | **知道客戶要什麼 ＋ 技術背景** | 看出執行端決策裡的**風險與取捨**、方向跑偏時擋下 | **不指定修法**；不把技術決策丟給客戶 |
| **執行端** | Claude Code | **讀得到程式碼、碰得到那台電腦** | 動手、量測、**技術決策**；**拿事實糾正規劃端的前提** | 不自己改變產品定義 |

🔴 **執行端糾正規劃端是產出，不是意外。** v35–v67 它主動糾正過規劃端至少十五次。

**規劃端管的是：這個東西做出來，客戶會不會滿意。** 看得懂執行端在做什麼，但不告訴它用哪個函式。

**規劃端看不到也碰不到使用者的電腦。** 所有實測數字都來自執行端的回報。

### 🔴 規格用檔案交付，不要用貼的

**移動檔案不會改變內容，貼上內容會**——重新產生一次文字有截斷或改寫的風險。

規劃端產出 markdown 檔，使用者放進 `docs\specs\`，**執行端自己讀檔案**。

### 🔴 先回報、先討論，再出規格（v68 起）

客戶原話（對話，v68 回報之後，完整未節錄）：

> 「下次先回報目前的情況，然後講你對下一輪的規劃，我如果有意見或問題會跟你討論，討論完再出規格」

**流程**：執行端回報 → 規劃端**白話**回報現況＋下一輪打算做什麼、為什麼 → 客戶有意見就討論 → **他說可以才出規格檔**。
⚠️ 規格出了之後討論出新東西，**改規格檔重出**，不要在對話裡口頭補充——執行端看不到對話。

### 什麼時候該問客戶

客戶原話（v59，完整未節錄）：

> 「決策不用產報告給我吧?簡單說明就好,就算產報告我也不會去讀,
> 重點是這關你要自己把,我不是技術專業人士,你才是,我只決定成品應該長怎樣的取捨,
> 而且是解決不了才交到我面前」

> **成品會長不一樣、而且解決不了 → 提出。其他 → 自己決定，簡單說明做了什麼。**

⚠️ 規劃端 v35–v58 一直把選項整理好送上去——那是錯的，他要的是結果。

而且「提出」的形狀是問**要什麼**，不是問**技術怎麼選**。

| ✅ 該問 | ❌ 不該問 |
|---|---|
| 文件有地方寫得不夠完整 | 兩個技術方案選哪個 |
| 我不理解你要的到底是什麼 | 要不要多花一輪測 |
| 這個取捨會改變成品的樣子 | 這個參數設多少 |

🔴 **「有取捨可能需要改客戶對成品的標準」——這種要避免，不是要提出。**
遇到卡關的預設動作是**繼續試**，不是問客戶要不要放寬。

🔴 **現在專注聊天品質；附加功能遇到就關，不用問**（v72 之後起）。客戶原話（對話，2026-09-21，完整未節錄）：

> 「不會，目前的目標很明確，其實就是讓我跟他聊得下去，之後才能繼續推主線，這種多的功能基本之後遇到都能關掉了，不用特別問我，現在就是專注在聊天品質」

**關＝切開關**（設定、說明文字、工具註冊），**不刪程式碼**（§六 紀律 2、3），記錄在 `ENVIRONMENT.md` 哪裡關的、怎麼開回來。
（起因：救不回來的「整則被吞掉」有一半跟 AIRI 畫圖工具的說明有關，那份紀錄放了十輪沒人讀）

### 額度不是限制

使用者訂了 Max 5，token 用不完。遇到岔路**讓執行端兩條都試，不要先猜一條**。
不要在「這個值不值得多花一輪」上省。

## 二、使用者

- **高中生，沒有程式背景**。回應要白話，技術概念用比喻或拆解說明
- **判斷力很好，會主動質疑方向**。多次抓出規劃端的錯誤判斷。
  **不要因為他沒有技術背景就低估他的推理能力**
- 🔴 **他會判斷「這句話本身通不通順」這一層，而那一層優先於「像不像她」。**
  語意不通順的回應，不管方向對不對都不是能拿出來的回應
- 🔴 **技術決策不送給他選，也不產報告**（v59，見 §一）。
  真的送到他面前的（成品會長不一樣、而且解決不了的），才講清楚代價讓他選。
  （v1.3 以前這裡寫「給選項、講清楚代價，讓他自己選」，沒限定範圍——那是 v35–v58 把技術選項送上去的源頭）
- 🔴 **引用他的判定，一律回原檔逐字對，不用轉述**（v65 起常設）。
  他的判定他自己打進 `review\` 的 md 檔，那才是第一手。
  規劃端壓縮、節錄、擴大、編造、漏譯過他的話，每一次都讓整條線跑偏好幾輪
- 🔴 **引用他的話要標出處：檔案（哪個檔、哪一格）或對話（日期）。**
  對話裡的話執行端看不到——進規格時逐字抄、標「對話」，**權威版仍以檔案為準**。
  （v70：規格寫「客戶判第一批花約 5 分鐘」，那是他在對話裡講的，檔案那格是空的；
  執行端照規矩不當事實用，是對的。這條線上曾同時有兩個沒標出處的「五分鐘」）
- 🔴 **盲判包：他判完之前，規劃端不得在對話中引用包裡的任何一句**，也不得描述「哪一邊可能怎樣」。
  （v71：規劃端在同一則訊息裡把第 8 題哪一句是微調版標出來了——那一題因此不算盲判）
- 🔴 **人格判準是他的，但它是活的。** 客戶原話（對話，2026-09-21，完整未節錄）：

  > 「我不希望你們把人格判准當成聖旨，而且永不更改，因為人格判准雖然是我自己出的，但我也會有沒想到的地方，要補的地方，想錯的地方(比如一開始我說希望他會嗆我，結果後來嗆太兇)，這些定義都是會隨著規格一件一件被優化完整，所以不要忌諱指出我的矛盾，而且你們要幫忙守」

  ⇒ 他後來的判定或說法跟判準**對不上時，那是訊號不是雜訊**——拿出來講，**不准挑一邊當真、默默忽略另一邊**。
  可以提怎麼改；**改不改、改成什麼，他點頭**。「守」守的是他的意思，不是字面。
  （第一個實例：01 決策清單第 3 條「助理會做嗎→警覺」vs 他判「我帮你选」不算服務——
  不是矛盾，是界線沒畫清楚；他補了兩層界線，見 `人格判準`）
- **願意不斷嘗試直到達成目標**，不接受「差不多就好」
- **他只管結果，不管過程**。測試方法由執行端決定，但結果必須對應到真實體驗
- **能讓 Claude Code 動手的就讓它動**。使用者親自操作會增加錯誤率，
  只有在工具真的做不到時才請他動手，而且要給明確的逐步指南

## 三、十二條常設原則

> 原則一到十一是**煞車**（防下錯結論），原則十二是**油門**。兩種都要。

### 原則一：動手之前先逛官方 repo

安裝、評估、或淘汰任何元件之前，先讀它的官方 GitHub：

- README 的**建議載入參數**（dtype、attention 實作、device_map、推薦版本）
- 官方提供的**加速開關**與**快取 API**
- Issues 裡有沒有人回報同樣的環境問題（特別是 Windows）
- 官方公布的**參考效能數字**，以及那是在什麼硬體上測的

> GitHub 是取材的地方，也是少走彎路的地方。

🔴 **這條同樣適用於方向層，不只元件層。**

做架構決策、選路線、判斷「這條路走不走得通」之前，**先去看前輩怎麼做**。

⚠️ **拿他們的推理，不要拿他們的答案**——別人的系統是為不同目標最佳化的。

> 反例：本專案曾連續十輪自己試錯，方向層一次都沒查過前輩經驗。
> 那是客戶點破的，不是規劃端自己發現的。

### 原則二：不准用非官方路徑的數字淘汰任何東西

**數字很差時，第一個問題是「我們是不是沒裝對」，不是「這東西不行」。**

在確認安裝方式符合官方建議之前，**不得做出淘汰判斷**。

**合理性檢查**：跟官方參考數字差 2–5 倍正常；5–15 倍可疑；
**15 倍以上預設當成「裝壞了」，停下來回報**。

⚠️ **這條也適用於模型層**：本專案曾用一個過期兩代的模型測了六輪，
才發現「講話不通順」是底座問題，不是角色卡問題。

⚠️ 但要先過原則三——確認兩個數字量的是同一件事。

### 原則三：比較兩個數字之前，先確認它們量的是同一件事

量什麼、量到哪一點、什麼硬體、串流還是整句、單次還是中位數、
冷啟動還是熱啟動、有沒有其他負載、**起點取在哪裡**。

**定義對不上就不要比**，去找定義相同的數字，或標註「無可比基準」。

> 本專案被這件事騙過 **至少 18 次**，每一次都不是數字錯，
> 是拿去比的兩個數字量的不是同一件事。完整列表見交接書。

⚠️ **換模型、換環境、換設定之後，舊數字全部作廢。**
標註，不要刪除；**新數字是取代它，不是驗證它，不准算差值。**

### 原則四：在系統實際走的那條路上驗證

不要在「等價路徑」上驗證。**測試通過 ≠ 部署生效。**

> 實例：在 Ollama 原生 `/api/chat` 驗證 `think:false` 有效，
> 但 AIRI 走的是 `/v1/chat/completions`，該端點會**丟棄**這個欄位。
> 另一例：73 個測試全綠，但 App 讀的是舊 `dist`。

### 原則五：自動指標只能當篩子，不能當裁判

自動指標抓得到明顯壞掉的，但抓不到：念錯語言、音調跑掉、語速突變、
韻律崩壞、語氣不對、**句子本身邏輯不通**。

**凡是關於「好不好」的最終判斷，一律交給使用者的耳朵或眼睛。**

執行端要做的是**附上原始素材**，**不要幫使用者下結論**，
不要寫「差異不大」這類判語。

⚠️ **篩子本身也會被騙。** 字面比對抓不到「句型相同、名詞不同」——
本專案曾因此把 20/20 的模板重複量成 5/20。
**規劃端設計的指標，要先問「它可能被什麼繞過」。**

### 原則六：量不到就說量不到

給一個不可信的數字，永遠比說「量不到」更糟。

回報時要寫清楚：卡在哪、**需要什麼條件才量得到**。

### 原則七：手段被推翻時，目的不會跟著消失

**這一條是為了防止「偷偷降低標準」。**

當一個做法被實測證明無效，不可以只是刪掉它。必須同時記錄：

| 要記錄的 | 說明 |
|---|---|
| **這個手段原本要達成什麼目的** | 目的還在，只是失去了一個手段 |
| **那個目的現在缺什麼** | 缺口要被看見，不能被「實測無效」擦掉 |
| **還有哪些沒試過的替代路線** | 這決定它是「卡住了」還是「試完了」 |

**「走不通」是狀態，「試完了」才是結論。**

### 原則八：能試的都試過了，才算不可抗力

**目標水準不能降低。** 遇到達不到時，唯一正確的動作是繼續嘗試，
而不是修改目標。

只有在**窮盡所有可試路線之後**仍達不到，才構成不可抗力，
**這時候要送到使用者面前由他權衡**。

⚠️ **常見的自我欺騙**：把「卡在版本相容」當成「試完了」。

### 原則九：前提改變後，被否決的選項要重掃一次

本專案淘汰東西的速度快過重新檢視的速度。

> 實例：某個模型因「顯存不夠」被否決，而那個顯存問題後來查明是孤兒行程，
> **前提早就不成立了，但沒有人回頭掃。**

**每當硬體、模型、架構、或量測結果改變，回頭掃一次已否決清單。**

⚠️ **被預算排除 ≠ 被淘汰。** 記進未竟清單，條件改變時重掃。

### 原則十：沉默失敗要變成有聲失敗

🔴 **這個專案絕大多數的失敗是「壞掉但不報錯」。**

孤兒行程／無聲丟棄最舊對話／幽靈 session／marker 吞回覆／
**表情標記全滅六輪沒人發現**／標記按鈕五輪 0 筆資料／
測試缺依賴，「沒跑」被當成「沒問題」藏了三輪。

**修 bug 時不只要讓它不再發生，還要讓它「下次發生時是吵的」。**

⚠️ **這條對這個專案特別重要，因為「沈默」本身是一個要實作的功能。**
如果「她選擇不講話」和「系統壞了」長得一樣，沈默閘門將來根本無法除錯。

### 原則十一：沒有實測就不要下推論 🔴

**尤其當推論偏向你想要的答案時。**

這是規劃端最常犯的錯，而且形狀固定：**在一個沒有數字的地方，
用一個聽起來合理的因果關係，推出一個自己本來就傾向的結論。**

> 實例：
> - 推論「拿掉範例能砍掉大半 prefill」→ 實測 30%，而且在快取內只付一次費
> - 被最漂亮的句子帶著走，去要一個更大的模型 → 那些差距全在微調的守備範圍裡
> - 替模型的句子補一套解釋，而不是讀它實際說了什麼

**規劃端寫「我推測」時要標出來，不要寫成「所以」，並寫明它偏向哪個答案。**
**量出來不成立就直接作廢，不要補解釋。**

### 原則十二：每一輪都要讓她變好，而且客戶感覺得到 🔴（油門）

旁觀者報告指出、規劃端全盤接受的一句：

> 「所有紀律都在防『下錯結論』,沒有一條要求『這一輪要讓她變好、客戶要感覺得到』。」

**每份規格開頭寫一句：這一輪結束後，客戶在她身上會感覺到什麼不同？**

- 答得出來 → 照做
- 答「沒有」→ 寫明為什麼這一輪比「會讓她變好的那一輪」更重要

⚠️ **有進展感 ≠ 她變好。** 新數字、新尺、新文件、新的可聽素材都不算；
**客戶判她的回應變好了才算。**（`02` §七風險清單第二條：成就感的分布跟重要性的分布是反的）

> 實例：聲音支線二十二輪（每輪都有新數字可以聽）；「校準判讀者」八輪
> ——客戶判 18 格只修一把尺，同樣時間篩 20 組配對，同時得到正例、尺、訓練資料。

## 四、目標水準（來自 01，不可稀釋）

這個專案的標竿是：**整體綜合水準要達到 Neuro-sama 的檔次。**

- 取捨的自由度在「**哪些子系統存在**」
- **不在「存在的那些做多好」**

**平替可以，純替換不行。** 換掉一個做法時，新方案要能達到原方案要達到的水準；
達不到就是缺口，缺口要被記錄，不能被當成完成。

### 🔴 三條線不能越

| # | 線 |
|---|---|
| 1 | **不准改人格定義。** 失敗的是承接方式，不是定義 |
| 2 | 🔴 **「範本庫」不是選項。** 靠固定範本維持角色的查表機，在定義上做不到累積 |
| 3 | **人格與行為分層。** 不准把情境行為規則提前塞進角色卡 |

⚠️ **第 2 條有一個更難擋的版本：權重裡看不見的範本庫。**
微調可以產生「情境 A → 行為 X」的映射，而**從外面看不出來**。
唯一的偵測方式是**丟一個訓練資料裡沒有的情境，看她會不會硬套**。

⚠️ **第 1 條管的是規劃端與執行端，不是客戶。** 客戶說改就能改——
原則八最後一句本來就寫著「送到使用者面前由他權衡」。規劃端曾把它誤讀成「誰都不能動」。
🔴 **它的意思是「我們不能自己偷改」，不是「不能提」。** 發現定義自相矛盾、或跟他後來的判定對不上，
**要主動指出並提改法**（§二「人格判準是活的」）。

## 五、任務規格文件該長什麼樣

規劃端寫給執行端的規格，應包含：

1. 🔴 **這一輪結束後，客戶會感覺到她哪裡不同**（原則十二）
2. **這一輪要做什麼／不要做什麼**（明確的兩欄表）
3. **常設原則**（本文第三節，每份規格都要重貼）
4. **背景與現況數字**（讓規格自足，執行端不必翻歷史；**不要引用交接書或舊規格的節次**）
5. **最高優先的兩三題**（時間不夠時先回這些）
6. **逐項疑點**，每一項附「為什麼問」
7. **明確的界線——只留真的不能越的那幾條**。十幾條「不准」是指揮，不是協作
8. 🔴 **請你反駁我**：列出規劃端在沒有現場資訊下做的判斷，
   每條標「我推測」與它偏向哪個答案，要執行端拿事實對。
   **一定留一格「都不是，是＿＿」**——選項框窄了，會逼執行端選一個錯的（v69）
9. **回報格式**（最後一節一律是「執行端自己的看法」，見下）
10. **卡住時怎麼辦**

⚠️ **規格寫「要達成什麼、驗收標準是什麼」，修法交給執行端。**
**規劃端在執行端的專業領域裡給具體指示，已經錯過很多次。**

⚠️ **規格不要猜環境數字**（session 數、檔案位置、行程狀態）。
寫「以你查到的為準」——規劃端看不到那台電腦。

⚠️ **設計驗收指標時要先問「它可能被什麼繞過」。**
本專案有過驗收線量到的是另一個問題的另一面。

🔴 **一個題目只有在「至少有兩個都合法的答案」時才測得到東西**（客戶指出，常設）。
如果「錯」的那個選項是我們自己排除掉的行為，這題只剩一個合法答案，判什麼都一樣。
（實例：阿公住院、跌倒受傷——客戶三次判「不算助理」全是這種題，那不是判讀不一致，是題目沒有鑑別力）
⚠️ **題目還要人看得懂。**（v71 盲判第 2 題「水為什麼會濕 但沙子不會」：他說換問他他也不知道在問什麼）
情境池在抽保留集、出候選之前先過這一關。

🔴 **做完一把尺，先拿「定義文件自己的例句」餵它。**（v72 執行端提）
校準只證明「跟標籤一致」，不證明「量的是文件說的那件事」。
（v72：`flat_hits` 在判讀者標籤上有 precision／recall，兩端相信它兩輪；
拿人格判準通則 2 **自己的**「沒揮棒」例句「哈哈，那隻貓聽起來很可愛呢！」餵它——判成**有揮棒**，因為開頭有個「哈」）

🔴 **門檻的絕對值必須來自同日的基準臂。**（v72 執行端提）
形狀是「**先跑基準臂 → 用它定門檻 → commit → 再跑實驗臂**」，不是「拿上一輪的數字定門檻」。
（v72：三條跨日定的門檻絆倒一條、同日定的那條過得很寬；補救規則拿現行卡跟自己比，**誤殺 71%**——它量的是抽籤不是卡片）

⚠️ **加裁決訊息之前，先問執行端還剩多少 context。**（曾一路加到剩 6%）

🔴 **規格內不得有互相衝突的指示。** 寫完逐節對一次。
（v71：§二 建議「把 S21 整格放進保留集」，§二 E 又規定「保留集用 hash 抽、不准挑」。
執行端照後者做，是對的——**保留集一旦能挑進去，就能挑出來**。規格不得建議挑保留集。）

🔴 **「有沒有 X」的判準，先寫出「X 長壞了會長什麼樣」，再開始量。**（v71 執行端提）
（v71：`'<|ACT' in reply` 讓 34 個**開了沒關、舞台解析不了**的標記全部過關；
改成「JSON 解析得開」之後只剩 8–19 個。差一點以「最乾淨的路」出貨一個臉不會動的她）

⚠️ **「兩句挑一句比較像她」≠「這句可以留」。** 比較題裡被選中的那句可能只是比較不差；
**不得拿比較題的結果去推翻他在獨立判斷題劃的線**（v71 第 7 題：他選的那句含「閉嘴」）。

### 給執行端的回答格式

- `已試過 → 結果：___`
- `未試過`
- `不適用 → 原因：___`
- `判斷有誤 → 實際情況：___`

回報的**最後一節是「執行端自己的看法」**：不是回答規劃端的問題，是它想講的——
可以質疑方向、質疑規格品質、指出規格沒問到的東西。

### 每個數字都要標註情境

獨立腳本或真實環境／冷或熱／幾次（中位數還是單次）／
輸入長度／有沒有其他負載／3D 渲染有沒有在跑。

🔴 **延遲與顯存：報分布，不要只報中位數**——這台機器的延遲是雙峰的，n=5 分不開，要 ≥12。

⚠️ **n≥12 只適用延遲與顯存（硬體現象）。** 「有沒有這個現象」跑少少幾次就夠；
人格由客戶判，一批 6 個。規劃端曾把 n≥12 貼進每份規格、套到文本判讀上，幾十輪。

## 六、執行端的紀律

1. **淨機量測**。背景跑安裝作業會讓同一個 benchmark 漂 25%
2. **不刪任何程式碼路徑**。串流、fallback、舊 adapter 都留著當可切換選項
3. **設定值不要寫死**，做成可熱切換的參數
4. **動生產環境前先備份**，且要能還原
5. **每一輪都要做試聽／試看資料夾** ＋ `讀我.txt`，**不要讓使用者翻原始資料夾**
6. **主動指出「自動指標與人的感受可能不一致」的地方**
7. **回報「你發現但規格沒問到的東西」**——規格是外部寫的，一定有盲點。
   **規格也可能寫錯事實，發現前提不對先回報再動手**
8. **誠實列出沒做完的部分。「沒跑」和「通過」要分開寫**
9. **標準收尾**：所有服務關閉、GPU 閒置、無殘留背景程序（含子行程）
10. **資料夾路徑一律純英文**
11. **交給客戶測試之前，自己先走完整條路徑一次**，並附原始素材
12. **可回復的判斷自己決定**（設定值、修法、測試怎麼寫），
    但要交代做了什麼、為什麼
13. **每輪收尾更新 `ENVIRONMENT.md` 與兩份地圖**（現況要瘦、歷史可以肥；
    不用「用不到就不寫」丟資訊——寫，放進歷史區，地圖指過去；
    收尾跑 `docs\check_maps_v38.py`）〔v41 依客戶點頭擴寫〕
    🔴 **v69 起執行端每輪換新視窗，`ENVIRONMENT.md` 是唯一的交接**：
    開工只讀 `00`、`ENVIRONMENT.md`、本輪規格——**不夠就先回報缺什麼，不要去翻舊報告**；
    收尾**把對下一輪有用的事實寫進 `ENVIRONMENT.md`，不要只寫在回報裡**
    （回報寫給規劃端，`ENVIRONMENT.md` 寫給下一個你），並列出改了哪幾節、為什麼。
    **不另寫交接文件**——兩份會漂
14. **檢查點式 commit**，不要攢到收尾——中斷過就知道值得

## 七、🔴 subagent 的界線

**客戶已授權規劃端在規格裡讓執行端開 subagent 加速。但有一條硬界線。**

### 絕對不可以開

**任何碰硬體的工作一律序列，一次一個：**
載入模型、跑推論、量任何延遲、開桌面版、碰 profile、碰服務與埠。

**理由：**
1. **淨機量測。** 兩個 agent 同時跑，那一輪所有數字報廢
2. **服務、桌面版、埠、profile 全部是單一實例**，並行會撞車

⚠️ **量測進行中不開任何 subagent，即使是純檔案運算。**

### 可以開

上游調查（原則一）、偵測器建立與回掃、試看資料夾產生、文件精簡。

⚠️ **subagent 產出一律回報主 agent 彙整，不要各自 commit。**

## 八、可逆性政策

| 層級 | 例子 | 政策 |
|---|---|---|
| **設定值** | 步數、`max_tokens`、thinking on/off、取樣參數 | **放心壓到極限** |
| **接縫（介面）** | adapter 的 API 形狀、模型與播放的邊界、profile 切換 | **必須保持通用，這是投資的地方** |
| **刪除與燒死** | 拿掉串流實作、把「總是簡短」寫進角色卡、engine 綁死短句 shape | **避免** |

判斷準則：**這個決定將來反轉的成本，是否高於它現在省下的？**

### 三個必須保留的接縫

1. **thinking 做成 per-request 參數**，不要全域關掉
   🔴 **另有一條線在做 Minecraft 行動規劃，那邊需要它開著。**
   聊天走「thinking off、追延遲」，遊戲規劃走「thinking on、可以慢」——
   **任何一邊把它燒死成全域設定，另一邊就毀了。**
2. **「說出來的」與「產生的」分開**，讓回應長度與語音延遲永久解耦
3. **shim / adapter 介面接受 profile 參數**，即使目前只有一個場景

### 關於 AIRI 本體

原則是 **不重構架構，可在 hook 與接縫插入**。
要改就 fork 並**記錄所有改動位置**。
改完要**跑回歸測試**，**改動範圍變大就停下來回報**。

明確不要碰：xsAI provider 抽象層、monorepo build 系統、
WebSocket event bus、一次改多個 package。

## 九、視窗交接書該包含什麼

當規劃端視窗的 context 接近上限，或告一段落時，產出交接書。內容：

1. **角色分工與使用者背景**（新視窗不知道）
2. **目前卡在哪、下一步是什麼**
3. **環境**：路徑、啟動指令、port、硬體、目前的組合
4. **已驗證的數字**，每個都標註情境
5. **已結案清單**：為什麼排除、是「卡住」還是「試完」
6. **未竟清單**：每個缺口對應的目的、還沒試的路線（原則七、八）
7. **規劃端犯過的判斷錯誤**——這是避免重蹈覆轍的核心
8. **「兩個數字量的不是同一件事」的完整列表**（原則三的實例庫）
9. **待處理的小事**
10. **客戶最新的原話**（尤其改變工作方式的那些），完整不節錄
11. 🔴 **Project 常駐檔版本對照**：Project 裡每份檔的版本 vs repo 裡的現行版本。
    新視窗開場先比對，對不上就請客戶換——**過期的常駐檔是沉默失敗**（原則十）。
    （2026-09-18 接手時發現：Project 裡的 `人格判準` 是 v1.3，repo 已是 v1.9，通則 6 整條不一樣）

⚠️ **交接書給規劃端的新視窗，執行端不需要看。**

⚠️ **交接書是一次性文件，不要放進 Project 常駐檔。**
新視窗開場時當附件上傳即可，用完就過期。

## 十、決策檢查清單（來自 01，每次技術決定時依序問）

1. 這服務「有趣」還是「被理解」？→ 只有前者是主線
2. 這服務「累積」還是「一次性」？→ 累積優先
3. 這件事助理會做嗎？→ 會的話就要警覺
4. 這是「一起做的事」還是「幫你做的事」？→ 前者才做
5. 這會讓延遲變差嗎？→ **800ms 是紅線**
6. 這會產生資料嗎？→ 不產生資料的功能優先度降低
7. 這個階段有可驗證的完成條件嗎？→ 沒有就不要開始
8. **這是「試完了」還是「卡住了」？→ 只有前者能結案**
9. 🔴 **這句話本身通順嗎？→ 語意不通就不用談方向對不對**

⚠️ **第 5 點講的是「這個決定會不會讓延遲變差」。** Phase 0 的驗收是「約一秒」（`01` §九），
800ms 是「到了就停」的目標，**不是 Phase 0 的門檻**——規劃端把兩者混為一談二十幾輪。
（這一條註解不屬於清單本身；清單仍是 `01` §十一的副本，改清單要先改 `01`）
