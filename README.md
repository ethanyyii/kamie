# Kamie：本地端 AI 角色的微調與評測

Kamie 是一個在自己電腦上運行的 AI 聊天角色。這個 repo 收錄的是我在這個專案裡自己寫的核心部分：**對開源底模做 LoRA 微調、怎麼評估她有沒有變好，以及讓測試和實際上線用同一份輸入的轉接層**。

> **先說清楚**：Kamie 的語言模型不是從零訓練的。我在開源底模 Qwen3.5-4B 上做 LoRA 微調，也試了 Gemma-12B 的 QLoRA。這個專案真正的工作量在資料、評測與判斷「微調到底有沒有幫助」。

> 這是**方法與核心程式的展示**，不是可以直接重現的專案：底模權重、訓練資料與角色卡含有私人對話，所以沒有公開。

## 系統架構

```
使用者（打字／語音）
   ▼
AIRI 前端（上游專案 moeru-ai/airi，不在本 repo）
   ▼  OpenAI 相容請求
llm-proxy/reasoning_proxy.py ── 轉接層（FastAPI，自寫）
   ▼
Ollama（本機推論，微調後的模型）
   ▼  串流回覆
轉接層記錄、監看 → AIRI → TTS 轉接（glm-tts/、omnivoice-tts/）→ 播放
```

### 轉接層為什麼要存在

前端送給模型的請求裡，會自動加入工具清單、介面元件提示和角色卡示範句。這會造成**測試時餵給模型的輸入，和上線時不是同一份**，評測結果就不可信。轉接層把這些東西逐項剝除或轉換（例如把示範句轉成 few-shot 訊息），每一項都能單獨開關；全部關掉時，請求逐位元組不變。

## 微調（`finetune-v92/`）

- Qwen3.5-4B，bf16 LoRA（r=16、α=16、all-linear）；Gemma-12B 用 QLoRA（NF4）。
- **只對目標句算 loss**：prompt 部分標成 -100，並用 assert 確認解碼回來真的只有目標句。
- 梯度累積 8、AdamW、warmup 加 cosine 衰減到 10%、固定亂數種子。
- 每 1/4 epoch 存 checkpoint，驗證 loss **依資料來源分開記錄**，再用評測挑 checkpoint。

## 評測方法

我覺得這是這個專案最重要的部分：沒有評測就微調，等於盲修。

- **三條評測軸**（`docs/specs/eval三軸設計-v1.md`）：
  1. 語言自然度：句子本身通不通。這條優先於像不像角色。
  2. 人格一致度：有沒有命中失敗清單（例如自稱助理、客服式回答）。
  3. 未見情境泛化：比較「見過」與「沒見過」的題目，偵測模型是不是在背訓練句。
- **先寫計畫再跑**：每一輪的實驗計畫先 commit，時間戳早於資料，避免看了結果才改判準。
- **盲聊**：聊天時不知道對面是哪個版本，聊完才揭曉。
- **校準**：先用已知答案的題目確認評分者的判讀一致，才拿去評新版本。
- **群集 bootstrap**（`mainline-v70/sieve_v70.py`）：同一個情境重放 8 次不是 8 個獨立樣本，所以以「情境」為單位重抽樣，算 95% 信賴區間。判定「變差」必須點估計超線，**而且**整段區間都在變差那一側，避免被雜訊誤判。
- **自動篩子**：抄訓練句比對、簡體字、固著詞等。

## 發現

- **行為跟著資料走，不跟著模型走。** 同一包資料分別訓練 4B 和 Gemma-12B，兩者的行為幾乎一樣。換更大的模型解決不了資料本身的問題。
- 資料裡幾乎沒有「角色自己想要什麼、對什麼好奇」的句子（約 0.8%），所以微調後她變得高冷、愛句點。下一步要補的是資料，不是模型。
- 評測工具本身也會錯。例如有一版評分尺把我判為「可以」的句子判錯了 30%，之後就改成每次先校準再使用；也曾經發現「訓練和上線用同一份輸入」的說法不成立，就加了勘誤而不改原文。

## 檔案

| 路徑 | 內容 |
|---|---|
| `llm-proxy/` | 轉接層與它的測試 |
| `finetune-v92/` | 訓練、轉檔、checkpoint 評估腳本 |
| `mainline-v*/` | 各版代表性的評測與分析腳本 |
| `glm-tts/`、`omnivoice-tts/` | TTS 轉接 |
| `character-cards/` | 角色卡的結構範本 |
| `docs/` | 評測設計與工作規則 |

使用者名稱等個人設定改由環境變數提供（例如 `KAMIE_USER_NAME`）。

## 環境

Windows、NVIDIA GPU（CUDA）、Python（torch、transformers、peft、bitsandbytes、fastapi、httpx、opencc 等）、Ollama。部分評測腳本依賴沒有公開的資料檔與模組。

## 關於 AI 協作

本專案以 AI 協作開發：一個 AI 視窗負責規劃規格，Claude Code 負責寫程式與跑實驗，我（簡翊森，GitHub：ethanyyii）負責出題、盲聊、判定結果、決定方向，並指出評測工具哪裡判錯。程式與腳本主要由 AI 撰寫。
